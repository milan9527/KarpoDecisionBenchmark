# 原始输入：小 batch 与 1 / 2 / 4 个 GPU 副本

用户要求保持原始输入，测试小 batch 与增加 GPU 副本。复用上一轮风控200特征、SOP完整200候选的请求文件，逐字一致；不压缩、不截断、不做候选筛选、规则分流或答案缓存。

模型为同一 revision 的 Karpo 4B，使用上一轮相同 FP8、CUDA Graph 与原生推理实现。BF16沿用既有质量参考，不重复性能测试。只捕获本轮需要的 batch 1–4 图；其余模型执行逻辑不变。

当前单类实例 G/VT 配额为64 vCPU，单台四卡 g7e.24xlarge 需要96 vCPU。复用原两卡 Spot 实例，并从其停止状态创建镜像，启动另一台同型号两卡按需实例。每张GPU一个完整模型副本。既有单卡实例保持停止。所有新增及既有实例结束后仅stop，不terminate，保留模型和EBS。

## 冻结矩阵

- 场景独立：risk、sop。
- 副本数：1、2、4；4副本由两台各2 GPU机器承担。
- 最大 batch：1、2、4；等待时间统一0ms，在现有队列内直接取可用请求，隔离batch大小影响。
- 每组合预热4×副本数×batch次，再完整质量测试（风控240、SOP104次观察），然后持续100并发60秒并排空。
- 质量集仅重复已有合成观察；不是新的独立样本。负载输入沿用上一轮tuning请求，逐条保存request SHA。
- 1/4副本按batch 1、2、4顺序；2副本按4、2、1顺序，减少固定时间顺序偏向。
- 每场景在4副本中，选择全部调用有效、合成质量>90%、持续100并发P50最低者，平局取吞吐较高者。再做一次预热及60秒持续100并发确认。
- 全部原始响应、失败、实际batch大小、GPU及主机编号、编码/排队/模型耗时均保留；不同batch可能存在浮点计算引起的选择变化，逐条核对。

共18个矩阵组合、2次确认，共20段60秒持续100并发测试。这里并发是始终维持100个尚未完成的请求，完成一个立即补一个；并非每秒固定100次。

## 计时与验收

完整HTTP响应P50≤500ms、100并发、合成质量>90%；同时报告失败数、P95/P99及500ms内完成比例。失败不能通过剔除来视为达标。

所有组合经过同一层本机HTTP分发器，转发原请求至未改动的原生服务。1/2副本只用本机，4副本增加AWS私网转发，包含该转发成本；不包含客户生产入口网络或特征查询。采用同一实例类型，但跨机器CPU/驱动及资源状态仍需记录核对。不能把四副本结果当成单台四卡实测。

SOP候选、参考答案、risk特征及样本顺序保持上一轮版本。质量对照使用上一轮FP8逐条响应，性能以本轮同路径1/2副本为扩展基线。

## 运行及证据

输入与执行源码SHA在GPU测试前冻结；历史实验文件不可覆盖。主机定期同步到已有私有结果桶，完成后自动关机；另设75分钟关机上限。停止状态和模型保留单独核实。未获得容量或运行失败时保留失败证据，不把推算值当测量。
