# Karpo 系列模型：完整 200 候选测试

目标：在一次模型调用中完整传入 200 个工具 / SOP 候选，测试更小的 Karpo 模型能否降低延迟并保持参考答案一致性。程序不进行业务域判断或候选筛选。

沿用 `concise-fp8-20261119` 的英文精简请求，逐字保留状态、说明、候选、顺序和参考答案。40 个原有合成案例、12 个边界案例，各测原序和反序，共 104 次质量观察。参考答案不进入模型输入。配对观察和重复请求不是独立新增案例，不能证明生产准确率或 SOTA。

代码固定为 `6600011eb5cf46232d056ec0717dc726146d29de`。权重 revision、请求 SHA256 和执行文件 SHA256 在运行前写入 manifest。

配置：

- 31B：FP8 + Triton Attention + CUDA Graphs，作为本轮同机参考。
- 12B：FP8 + Triton Attention + CUDA Graphs；BF16 + Triton Attention + CUDA Graphs。
- 9B、4B：FP8 + CUDA Graphs；BF16 + CUDA Graphs。Qwen 模型不启用 Gemma 专用的 Triton Attention。
- 同一 GPU 顺序运行，每个配置单独启动进程。最大输入长度设为 8192 tokens，超过长度的请求保留为失败，不截断输入；不同 tokenizer 的实际 tokens 分别报告。

每个配置先做 8 次预热，正式质量测试为 80 次原有观察和 24 次边界观察。四个 FP8 配置再测并发 1/2/4/8，每格 24 次。三个 BF16 配置只做质量及串行延迟对照。计划总计 1168 次调用，包括预热及重复请求。

客户端与服务运行在同一 GPU 主机，使用 loopback HTTP，计时到完整响应，包含预处理和排队。错误计入尝试分母，记录所有响应和失败。服务启动、编译时间单列。保持原有判分和计时实现，不用模型输出修改参考答案。

比较每个配置的正确数、P50/P95、100ms 内正确完成数、顺序稳定性、相对本轮 31B 新增错误，以及 FP8 与同模型 BF16 的选择差异。并发扫描用于观察吞吐和排队，不能代表持续高负载 SLA。

先复用保留的 RTX PRO 6000 实例；同步检查 B200 的区域、配额、Spot 和停止行为可用性。B200 如能执行，另建子实验并固定运行配置；不把文档数字当作实测结果。

测试完成或执行异常后退出模型进程、同步结果并停止 GPU。只 stop，不 terminate，保留实例及 EBS 上的模型文件。报告不包含费用计算。
