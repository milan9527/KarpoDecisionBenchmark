# 为什么风控选择六RTX，SOP选择八H200

选型依据是完整输入下的固定到达率实测：**风控四RTX在100 RPS下过载，六RTX通过两轮正式验证；SOP扫描1/2/4/8张H200，只有八卡通过100 RPS探测，随后完成两轮正式验证。** 当前均使用Karpo 4B、vLLM 0.34.0、FP8、每卡独立模型副本，最大batch固定为4。

本文引用原基准测试及其逐条记录。端到端包括客户端发送滞后、代理、排队、编码和模型响应；风控六卡还包含跨区域通信。公网CloudFront/ALB入口另行验证，结果见[部署与优化说明](DEPLOYMENT-OPTIMIZATION.zh.md#多卡部署达到的能力)。

## 单卡支持多少RPS、延迟多少

“支持的RPS”需要同时满足完整请求成功和延迟目标。下表先列出确实运行过的单卡测试；过载时完成的吞吐不能作为500ms以内的服务能力。所有低负载与过载探测均持续20秒。

| 场景与单卡型号 | 未过载的实测点：有效RPS / 端到端P50 | 向单卡发送100 RPS后的有效吞吐 / P50 | 过载时失败 / 计划 |
|---|---|---|---|
| 旧版服务资源风控，单RTX | **20.00 RPS / 44.95ms**，400次全部成功 | 28.80 RPS / 2197.88ms | 1363 / 2000 |
| SOP完整200候选，单RTX | **8.00 RPS / 116.02ms**，160次全部成功 | 10.40 RPS / 6139.89ms | 1731 / 2000 |
| SOP相同输入，单H200 | **8.00 RPS / 74.48ms**，160次全部成功 | 16.80 RPS / 3794.41ms | 1603 / 2000 |

单H200测试是在八卡`p5en.48xlarge`内只启用一个模型副本，其余GPU不参与该阶段；仍按整台EC2计费。SOP的RTX和H200测试使用相同输入、FP8及最大batch=4，但实例CPU等环境不同，结果代表各自测试部署。

**当前完整薅羊毛输入没有独立单卡RPS扫描。** 旧风控的20 RPS不能直接套用到新版输入。为说明当前每张卡实际承担多少负载，按六RTX和八H200正式测试的原始响应，重新统计每个副本在第30至120秒内的有效完成数和这些请求的P50：

| 当前输入及部署 | 卡池内每张GPU的实测有效RPS | 各卡端到端P50范围 | 范围说明 |
|---|---:|---:|---|
| 完整薅羊毛风控，六RTX | **15.46～17.51 RPS** | **63.25～90.58ms** | 两轮、六个副本；远端卡计入跨区域路径 |
| 完整SOP，八H200 | **每卡12.50 RPS** | **75.20～82.51ms** | 两轮、八个副本，全部在同一台主机 |

两组正式测试均为总到达率100 RPS、每轮120秒，零失败。这证明相应卡池内的每卡表现；它们不是“单卡隔离部署的最大达标RPS”。目前仍缺少新版薅羊毛独立单卡扫速，以及SOP单H200在8～16.8 RPS之间的边界扫描。

每卡有效RPS计算为`30 ≤ end_offset_s < 120`内的有效完成数除以90；P50取同一组请求的nearest-rank中位数。重算结果、源文件路径与SHA256见[每副本统计](../operations/gpu-sizing-20261121/per-replica.json)。

单卡原始摘要：

- RTX旧风控：[20 RPS](../experiments/vllm-rps100-20261120/results/runs/dual-fp8-v1/b4/r1/risk/low-load/summary.json)、[100 RPS过载](../experiments/vllm-rps100-20261120/results/runs/dual-fp8-v1/b4/r1/risk/rps100/summary.json)。
- RTX SOP：[8 RPS](../experiments/vllm-rps100-20261120/results/runs/dual-fp8-v1/b4/r1/sop/low-load/summary.json)、[100 RPS过载](../experiments/vllm-rps100-20261120/results/runs/dual-fp8-v1/b4/r1/sop/rps100/summary.json)。
- H200 SOP：[8 RPS](../experiments/vllm-sop-h200-20261120/results/runs/h200-fp8-v2/sweep/b4/r1/sop/low-load/summary.json)、[100 RPS过载](../experiments/vllm-sop-h200-20261120/results/runs/h200-fp8-v2/sweep/b4/r1/sop/rps100/summary.json)。

## 风控为什么需要六RTX

### 完整薅羊毛输入让四卡出现计算瓶颈

四RTX曾经支持旧版200特征风控，但旧输入为2263～2298 tokens。补齐薅羊毛行为、关系及规则后，最终完整输入为3216～3315 tokens。特征数量仍为200，实际模型处理的序列更长。

用最终同一输入、相同模型、batch=4、CUDA Graph powers及冻结复核阈值，对照四RTX和六RTX，两轮均按100 RPS发送120秒：

| GPU配置 / 轮次 | 稳态有效RPS | 端到端P50 | 失败 / 计划 | 每卡平均GPU利用率范围 |
|---|---:|---:|---|---:|
| 四RTX / confirm | 76.71 | 3313.69ms | 2564 / 12000 | 98.62%～99.13% |
| 四RTX / repeat | 76.71 | 3312.35ms | 2557 / 12000 | 98.87%～99.09% |
| 六RTX / confirm | 100.00 | 67.62ms | 0 / 12000 | 80.44%～90.07% |
| 六RTX / repeat | 100.01 | 68.11ms | 0 / 12000 | 82.18%～91.87% |

四卡GPU已接近满载，完成速度低于到达速度，排队后触发限流。扩到六个副本后，每张卡承担约16.67 RPS，实际各副本分布见上表，队列能够及时排空，整体P50回到约68ms。六卡增加的跨区域路径也计入结果。

这次改善来自副本扩容及负载分配，输入、模型、batch和复核规则保持一致。两轮性能由失败变为达标，不能将变化解释为更换了更小模型或减少了特征。

### 六卡是已验证配置，五卡尚未验证

四卡过载结果简单折算为`76.71÷4 ≈ 19.18 RPS/卡`。这只是相同环境下的容量估计，此时P50约3.3秒；它不是“单卡19.18 RPS且延迟达标”的实测。

若仅作线性估算，五卡约95.89 RPS，已低于100 RPS目标；六卡平均分配为16.67 RPS/卡，因此选择六卡进行正式验证有数据依据。**实际只对照了四卡和六卡，没有测试五卡，不能宣称六卡是绝对最低配置。**

六RTX满足了该风控输入的目标，无需为这次验证更换GPU型号。区域上保留俄亥俄四卡，受当时配额和容量限制把新增两张同型号RTX放在北弗吉尼亚；原基准的路由和网络细节见[架构说明](ARCHITECTURE.zh.md)。

依据：[四卡优化结果](../experiments/promo-opt-20261121/RESULTS.zh.md)、[四卡正式确认](../experiments/promo-opt-20261121/results/runs/review-calibrated-confirmed/confirm/summary.json)、[六卡正式结果与GPU采样](../experiments/promo-rtx6-20261121/RESULTS.zh.md)、[六卡正式确认](../experiments/promo-rtx6-20261121/results/runs/rtx6-calibrated-v1/confirm/summary.json)。

## SOP为什么选择H200、为什么使用八卡

### 同一SOP输入在H200上更快

SOP每次完整输入200候选，原测试序列约5696～5758 tokens。单卡、8 RPS低负载时，RTX P50为116.02ms，H200为74.48ms，H200部署的延迟降低 **35.80%**。

在向单卡发送100 RPS的过载探测中，RTX有效吞吐为10.40 RPS，H200为16.80 RPS，提高 **61.54%**。这说明H200部署对该工作负载有更高处理能力；两者此时均有大量失败和秒级延迟，不能把过载吞吐当作满足500ms的承载量。

因此，按照SOP全部使用H200的测试方向，继续用同型号H200扩展副本。当前证据证明该配置的性能可行性，尚未证明它在所有GPU选项中成本最低。

### 1/2/4/8卡扫描只有八卡通过100 RPS

以下均为完整SOP输入、FP8、最大batch=4；每个探测阶段20秒、计划2000次：

| H200数量 | 稳态有效RPS | 端到端P50 | 失败 / 计划 | 100 RPS探测 |
|---|---:|---:|---|---|
| 1 | 16.80 | 3794.41ms | 1603 / 2000 | 未通过 |
| 2 | 33.47 | 3764.33ms | 1206 / 2000 | 未通过 |
| 4 | 68.00 | 3688.17ms | 409 / 2000 | 未通过 |
| 8 | 100.00 | 76.09ms | 0 / 2000 | 通过 |

随后八卡完成两轮120秒正式验证，P50为 **76.58 / 76.24ms**，稳态有效吞吐均为100 RPS，24,000次全部成功。每张卡稳定完成12.50 RPS；第一轮各卡平均GPU利用率70.2%～76.1%，比四卡过载时98.7%～99.1%的水平留有余量。

从单卡过载吞吐16.80 RPS粗略估算，六卡分担100 RPS时每卡要处理16.67 RPS，接近该过载观测值；八卡只需每卡12.50 RPS。这个估算解释了选择更多副本的考虑，**没有测试5/6/7张H200，不能据此宣布它们一定失败或八卡是最低配置**。

实际EC2为`p5en.48xlarge`，整台提供八张H200，所有副本及代理可以同机通信。在该实例中只启用六张或七张卡仍按整台八卡实例计费，因此减少启用卡数本身不会降低这台EC2的计算费用。

依据：[H200全部扫描与GPU采样](../experiments/vllm-sop-h200-20261120/RESULTS.zh.md)、[1/2/4/8卡原始扫描](../experiments/vllm-sop-h200-20261120/results/runs/h200-fp8-v2/sweep/b4/)、[八卡正式确认与重复](../experiments/vllm-sop-h200-20261120/results/runs/h200-fp8-v2/confirmation/b4/r8/sop/)。

## 配置结论的使用范围

六RTX和八H200的卡数依据是**同场景完整输入下的实测过载与通过记录**。副本独立处理请求，单卡低负载延迟主要说明一次请求的响应速度；总RPS还取决于排队、批处理、路由和可用副本数，不能仅用`1000/P50`推导最大承载量。

这些基准结果支持当前部署选择，但不包含单卡最大达标RPS、绝对最小GPU数量、故障少一张卡时仍达标或生产数据分布下的承诺。当前公网风控另有两轮达标记录，SOP公网入口仍需独立稳定性验证，见[部署与优化说明](DEPLOYMENT-OPTIMIZATION.zh.md)。

本次仅复核已有记录并补充文档，没有启动GPU、重跑模型或调整batch。
