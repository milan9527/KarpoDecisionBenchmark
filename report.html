03

选择质量：本测试集参考一致

三组配置在两类质量测试中均与冻结参考答案一致；这些观察不能证明通用 SOTA。

QUALITY ≠ LEADERBOARD CLAIM

200 项合成 SOP

40 × 2 = 80快照 × 候选顺序 = 观察

40 个业务快照来自 20 类规则模板，覆盖 10 个业务域。每例分别使用原始候选顺序与反转顺序。

合成规则不代表 Redotpay 的真实政策。80 次观察并非 80 个独立业务案例。

已有支付快照

40 × 2 = 80快照 × 候选顺序 = 观察

从原 StrandsDecider 项目冻结复制 40 个支付快照，每次只有 2–6 个候选，保留原请求内容。

该集合可用于检查支付决策表现，不能替代 200 候选的生产评估。

04

并发增加，主要增加排队

200 项长描述 · 每个并发等级 32 次请求 · 有效吞吐包含尾部排空。

SERVER QUEUING

并发 1 / 2 / 4 / 8

所选配置的并发吞吐与 P95
并发数有效请求/秒P95 · ms

瓶颈在服务端串行推理

官方服务使用 Runner 锁串行处理模型推理。FP8 并发从 1 增至 8，吞吐仍约为 0.74 请求/秒，P95 则升至 10.72 秒。

增加 HTTP worker 不能直接视为 GPU 推理吞吐提升。不同请求需要限制排队、设置截止时间，并验证多副本或真正的批处理方案。

Server-Timing: model
包含 Runner 锁等待，不是纯 GPU kernel 耗时。

固定到达率测试采用 5 秒发送窗口，计入排空时间；当 P95 超过 5 秒时停止提升负载。这是短时负载检查，不是长期稳定性测试。

05

下一步：优化推理延迟

以下为依据本次结果的建议，尚未部署，也未计入模型测速。

RECOMMENDATIONS
01 / MODEL

保留 31B 作为质量基线

FP8 是本次最快路径。若新决策必须在 100ms 内完成，需要继续测试较小模型、蒸馏或分层路由，并用真实业务数据复核质量。

未对其他决策模型做本轮横向实测
02 / INPUT

缩短输入，验证整个流程

压缩候选描述，或先召回少量候选再决策。评估必须包含召回遗漏、路由错误及模型选择错误，不能只测已保留正确答案的子集。

20 项短描述在本次 FP8 扫描中仍超过 100ms
03 / CAPACITY

限制排队，验证吞吐

设置有界队列和请求截止时间，按实测吞吐规划 GPU 副本。验证多副本或批处理能否同时改善吞吐与尾部延迟。

按并发负载记录 P95 与 P99
